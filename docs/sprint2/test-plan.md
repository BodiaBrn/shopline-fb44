# План тестування продукту ShopLine (Спринт 2)

**1. Продукт і межі тестування:**
Об'єктом тестування є інтернет-магазин «ШопЛайн» (SPA на Angular, REST API на Laravel) та Java-модуль бізнес-логіки програми лояльності. Межі тестування охоплюють: публічний каталог товарів, кошик, покроковий процес оформлення замовлення, кабінет зареєстрованого покупця, контактну форму, а також бізнес-правила розрахунку знижок та вартості доставки (класи Cart, DiscountCalculator, PromoCodeValidator). Поза межами тестування залишаються: адміністративна панель, реальна інтеграція з банківськими платіжними шлюзами (оплата емулюється) та нарахування бонусних балів.

**5. Інструменти, середовище, тестові дані**
*   **Середовище:** Публічний тестовий демо-стенд Toolshop (https://practicesoftwaretesting.com), локальне середовище для Java-модуля (OpenJDK 17, Maven 3.9+).
*   **Інструменти:** Google Chrome (DevTools), Postman, Burp Suite, Apache JMeter, JUnit 5 Jupiter, Selenium WebDriver.
*   **Тестові дані:** Дефолтний обліковий запис (customer@practicesoftwaretesting.com / welcome01), вигадані email-адреси на доменах example.com для реєстрації, товари з наявного каталогу демо-стенду ("Pliers", "Hammer", "Cordless Drill"), тестові промокоди (PROMO10, FIX100).
**6. Ризики і припущення**
*   Періодичне скидання (очищення) даних демо-стенду Toolshop, через що створені акаунти та інвойси можуть зникнути. Пом'якшення: кожен тест-кейс має містити створення необхідних даних або використовувати дефолтні.
*   Асинхронність SPA-інтерфейсу (Angular), коли елементи завантажуються із затримкою, що може призводити до падіння автотестів. Пом'якшення: використання виключно явних очікувань (Explicit Waits) у Selenium.
*   Припущення: Зовнішні платіжні системи не задіяні безпосередньо, тому вибір способу оплати (наприклад, "Кредитна картка") завжди успішно генерує інвойс на боці застосунку.
